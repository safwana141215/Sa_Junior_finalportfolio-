Neon Runner Screenshot

Neon Runner: Cyberpunk Platformer

Tools: Unity, C#, Visual Studio Time: 6 Weeks Team: Solo

A fast-paced 2D platformer where players run and jump through a neon city. I built this for the Junior Programmer Pathway.

What I Did:

  • Programmed smooth player movement with jumping and wall-sliding using Rigidbody2D physics
  • Created enemy AI that patrols, chases, and attacks using C# state machines
  • Added neon glow effects with Unity's 2D lights and particle systems
  • Used GitHub to save different versions of my code so I could go back if something broke

What I Learned:

The first version of my jumping felt "floaty" and players didn't like it. After testing with friends, I learned about coyote-time—giving players a tiny window to jump after leaving a platform. This small change made the game feel much better. I also learned that GitHub is a lifesaver when you need to undo a mistake!

Chrono Cube Screenshot

Chrono Cube: Puzzle Game

Tools: Unity, C#, Visual Studio Time: 4 Weeks Team: Partner

A 3D puzzle game where you rewind time to solve challenges. Built for the Creative Core Pathway with a classmate.

What I Did:

  • Programmed a time-rewind system that records player positions and plays them backward
  • Designed 5 puzzle rooms using grey-boxing (simple shapes) before adding art
  • Created a clean HUD with energy meters and interaction prompts using Unity UI
  • Used lighting to show players when puzzle phases changed

What I Learned:

Working with a partner taught me how important communication is. We made a shared document listing who was doing what, and we met weekly to check progress. The hardest part was making the time-rewind work with physics objects—they kept clipping through walls. We fixed it by adding collision checks before moving objects. This showed me that games get better through testing, not just planning.

Iterative Design Process

How I go from idea to finished game through testing and refinement.

1

Brainstorming & Concept

📝

Mind Map

I start by writing down ideas and drawing mind maps. For Neon Runner, I looked at games like Celeste to see what makes platforming fun. I wrote a one-page document explaining the core idea: "Fast platforming with time mechanics in a neon city."

2

Wireframes & Planning

📐

Level Sketch

Before opening Unity, I draw level layouts on paper. I sketch where platforms go, where enemies should be, and where the "aha moment" happens. I also make flowcharts showing how screens connect: Menu → Game → Pause → Game Over. This planning stops me from getting lost later.

3

Grey-Box Prototyping

🧱

Grey-Box Screenshot

I build the game using simple shapes (cubes and planes) first—no art yet. This lets me test if the jumping distances feel right and if the level is fun. For Neon Runner Level 3, grey-boxing took 2 hours, and testing showed the jumps were too hard. Fixing the spacing took 5 minutes in the grey-box, but would have taken hours if I had already added art.

4

Playtesting & Fixing

🎮

Playtest Notes

I have friends play my game and watch where they get stuck. In Chrono Cube, players kept missing the tutorial for time-rewind. Instead of adding more text, I made the game slow down automatically to show the mechanic in action. This "show, don't tell" approach worked much better—tutorial dropout went from 40% to almost zero.

5

Final Polish & Documentation

✨

Final Build

In the final phase, I add art, sound, and UI polish. I also write a Game Design Document (GDD) that explains what the game is, how it works, and why I made certain choices. This document helps me remember my decisions and shows teachers or employers that I can plan professionally.

Games for Change 2025

Empathy Engine

Theme: Social Justice Team: 3 people Time: 48 hours

A narrative game where players see the world from different characters' perspectives. Built for the G4C Student Challenge.

My Experience:

This was my first game jam, and the 48-hour deadline was intense. We had to cut features to finish on time—we aimed for a 10-minute experience instead of something longer. I handled the programming while teammates wrote the story and made art. We used GitHub to share code in real-time. We didn't win, but the judges said our dialogue system was surprisingly advanced for a game jam. I learned that working fast means choosing what matters most.

Emoti-Con CS Fair 2025

Neural Nexus

Theme: AI & Humanity Solo Entry Time: 3 months

A Unity simulation where you train an AI companion through positive reinforcement. Submitted to Emoti-Con NYC.

My Experience:

I had to present this to judges who weren't all programmers, so I practiced explaining why I chose certain code solutions in simple terms. I did a live demo and answered questions. I placed in the Top 10 out of 200+ entries, and judges specifically praised my presentation and clear documentation. InfyAPP Challenge 2025

EcoQuest

Theme: Sustainability Team: 4 people Time: 6 weeks

A web app that gamifies environmental actions like recycling and saving energy. Uses game design ideas in a non-game app.

My Experience:

I applied game design concepts like daily challenges, streaks, and progress bars to motivate real-world behavior. We used Agile sprints with a task board to stay organized. One challenge was making the app fun without being addictive—we added "healthy limits" so users wouldn't feel pressured. This project showed me that game designers have a responsibility to think about player wellbeing, not just engagement.

Challenges I've Faced

Scope Creep (Adding Too Much)

Early on, I wanted every cool idea in my games. This caused me to miss deadlines. Now I define a Minimum Viable Product (MVP)—the simplest version that works—and save extra ideas for later. I keep a "parking lot" list for features that don't fit the current project.

Art & Visuals

I'm stronger at code than art. Instead of avoiding this, I learned Unity's Shader Graph and VFX Graph to make cool effects through code. I also collaborate with artistic teammates and practice describing what I need visually so they can help.

Accepting Feedback

I used to take negative playtest feedback personally. Now I understand that if players are confused, the design is unclear—not the players. I write down patterns from multiple testers instead of reacting to one person's opinion.
